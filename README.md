# EVERSTAR — Memories Beyond Time

EVERSTAR keeps personal memories as encrypted records and time capsules that remain sealed until their chosen opening date.

## Current implementation

- React + Vite interface with account sign-up, sign-in, sign-out, password recovery and password update.
- Supabase Auth sessions with PKCE.
- Durable Postgres storage; no localStorage fallback for private memory contents.
- AES-256-GCM encryption performed in a Supabase Edge Function. The encryption key is a server-only secret and is never sent to the browser.
- Capsule list responses hide titles and contents before the unlock timestamp.
- Memory retrieval checks ownership and unlock time on the server before decrypting.
- Private Storage bucket; uploads and short-lived download URLs are issued through an authenticated server function after ownership and unlock checks.
- In-app notifications are generated by a Postgres scheduled job when capsules become due.

## Important setup boundary

The GitHub code is not yet connected to a Supabase project. Do not enter private memories until the backend setup has been completed and verified. The repository intentionally contains no Supabase service-role key, encryption key, SMTP password, or VAPID private key.

### Required project configuration

1. Create a dedicated Supabase project for EVERSTAR.
2. Apply migrations in supabase/migrations/ in filename order. Confirm that the public schema is enabled for the Data API; newer Supabase projects may not automatically expose newly created tables. The browser roles still receive no direct access to the private memory tables.
3. Deploy memory-api and media-api Edge Functions with the shared files under supabase/functions/_shared/.
4. Set the Edge Function secrets:
   - MEMORY_ENCRYPTION_KEY: base64 encoding of exactly 32 cryptographically random bytes.
   - APP_ORIGIN: the exact production site origin; add localhost only for development.
5. Add the project's URL and publishable key to a local .env file using .env.example as the template. Never use the service-role key in the frontend.
6. In Supabase Auth URL configuration, set the production site URL and allow the local development URL plus the production password-recovery redirect.
7. Configure a trusted SMTP provider before inviting real users; Supabase's default email service is intended for limited testing.
8. Run the build and security checks before deployment.

### Local development

    npm install
    cp .env.example .env
    npm run dev

## Time-capsule security model

- The browser never receives the encryption key.
- Postgres tables containing encrypted memory payloads have RLS enabled and no direct grants to browser roles.
- Edge Functions authenticate the Supabase user and scope every memory query to that user ID.
- The Edge Function refuses to decrypt or return a capsule until the server clock reaches unlock_at.
- Attachments live in a private bucket. The browser gets a short-lived download URL only after the server checks ownership and unlock time.
- The scheduled SQL job creates an in-app notification once per due capsule. Browser push delivery is a separate opt-in layer and is not yet enabled.

## Security notes

- Keep the encryption key backed up securely. If it is lost, encrypted memories cannot be recovered.
- Rotating the encryption key requires a planned re-encryption migration; do not replace it casually.
- Do not commit .env, service-role keys, encryption keys, VAPID private keys, user exports, or subscription payloads.
- This implementation still needs a live-project security review, RLS/advisor checks, functional tests, and deployment verification before it should be treated as production-ready.
